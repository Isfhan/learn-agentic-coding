# 🧭 AI Product Manager — Adjacent Track

> **⏱️ Time:** ~10 hours of this roadmap (light touch) · **Track:** Tier 2 (adjacent) · **Start:** Step 00

The top-paying non-code path in AI: figuring out *what* to build with AI and why, then guiding engineers who build it. You don't need to write the code — but you need to understand it deeply enough to ask the right questions, set the right evals, and kill the wrong ideas early.

---

## 💼 What this role actually does

- Decides which AI features are worth building (opportunity + risk).
- Writes the spec, the acceptance criteria, and the "what good looks like" definition ([Step 13.5](../steps/13.5-spec-driven-development.md)).
- Pushes for **evals instead of vibes**: "how do we know the agent is better?" is your job ([Step 14](../steps/14-evals-testing.md)).
- Owns the go/no-go on release and the rollback plan ([Step 15](../steps/15-security-safety.md)).
- Translates between executives, customers, and engineers.

## ➕ Role-only additions (what the steps don't cover)

- **Framing exercises:** "AI answers → AI executes" — learn to evaluate agentic features by *outcome*, not demo.
- **Eval reading:** ask engineers for the pass-rate trend, not "it feels good." (Step 14 gives you the vocabulary.)
- **Cost governance:** context engineering ([Step 13](../steps/13-context-engineering.md)) is also your budget lever.
- **Risk ownership:** know when a feature needs human-in-the-loop ([Step 15](../steps/15-security-safety.md)).

---

## 🚀 Track capstone

Write a **product spec** (not code) for one agentic feature:

1. Problem statement + target user + success metric.
2. The spec (use GitHub Spec Kit conventions from [Step 13.5](../steps/13.5-spec-driven-development.md)).
3. A 10-case eval plan with pass criteria ([Step 14](../steps/14-evals-testing.md)).
4. A risk section with guardrails and a rollback plan ([Step 15](../steps/15-security-safety.md)).
5. Publish it with your analysis of one shipped AI product's mistakes.

## ✅ Self-check

1. Can you review a spec and find the ambiguity an agent would misinterpret?
2. Can you design "what good looks like" as measurable evals, not adjectives?
3. Do you know the top risks of agentic features and who approves them?
